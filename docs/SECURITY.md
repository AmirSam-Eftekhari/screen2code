# SECURITY: the Screen2Code security model

> **Implementation status:** this is a design document. For what is actually implemented, measured, and different, see [STATUS.md](STATUS.md) and [ADR-0002](ADR-0002-implementation.md); they take precedence where they differ.

Status: Draft. Depends on: ADR-0001 (A3, D6), IR_SPEC.md r2 (sections 16, 18), PIPELINE.md, GENERATION.md, EVALUATION.md.
Scope: the engineering security model. The public vulnerability-reporting policy is the repository-root `SECURITY.md` (created with repository scaffolding in Phase 1); this document is its technical basis.

## 1. Trust boundary (explicit)

```
 UNTRUSTED                                   TRUSTED (validated, sanitized handling)
 ---------                                   ----------------------------------------
 imported images ----> S0 decode (limits) -->  core engine, stage runner, IR validator
 model / provider outputs -------------------> schema validation, size limits
 the IR derived from the two above ----------> treated as untrusted data by generators
 generated code and projects ----------------> never executed automatically
 plugins (trusted-code by design, section 8) -> only if the user enables them
```
- Imported images, model outputs, the IR derived from them, and all generated code are untrusted input. The IR is untrusted input to every generator (IR_SPEC T-1..T-5).
- Generated code is never executed automatically. Static HTML may be rendered offline with JavaScript disabled. React/Next.js build or execution requires explicit user action and an isolated execution boundary.
- The exact Windows isolation mechanism is an OPEN SPIKE (section 5.3). It is not solved and no document, UI string, or release note may present it as solved.

## 2. Threat model

| Threat | Vector | Control | Section |
|---|---|---|---|
| Path traversal / arbitrary write | output directory, asset names, IR names, manifest | confined writer; names sanitized | 3 |
| Malicious or oversized image | decoder bugs, decompression bombs | header checks, limits, subprocess workers | 4 |
| Malicious SVG | vector content in assets | SVG only generated by us; imports rejected; sanitizer for any plugin-provided SVG | 4 |
| HTML/script injection | OCR text, names, alternatives into generated code or the UI | escaping at every sink; UI never injects raw HTML | 6, 9 |
| Prompt injection | text inside screenshots reaching a VLM/LLM | no tool access, structured output, untrusted results | 6 |
| Arbitrary code execution | building or running generated projects | tiered execution; explicit action; isolation boundary | 5 |
| Dependency attack | installing packages for generated projects | pinned allowlisted template, lockfile with integrity, no install scripts | 5, 8 |
| Supply chain | our own dependencies, models, browser | locks with hashes, checksums, SBOM, signed releases | 8 |
| Credential leak | remote provider keys | OS credential store only | 7 |
| Privacy leak | personal data in screenshots | local-first, redaction, remote opt-in | 7 |
| Malicious plugin | entry-point code | trusted-code model; disabled by default | 8 |
| IPC abuse | desktop-to-sidecar channel | stdio only, no listening port, minimal command surface | 7 |

## 3. Filesystem boundaries
- Every core file operation goes through a `Workspace` object holding the project root and an explicit set of allowed roots (project dir, models dir, cache dir, user-chosen output dir). Paths are resolved against these roots; anything resolving outside is rejected after canonicalization.
- Rejected inputs: `..` segments, absolute paths in IR-derived names, drive-relative paths, UNC paths, reserved Windows device names (CON, PRN, AUX, NUL, COM1-9, LPT1-9, with or without extensions), trailing dots/spaces, alternate data streams (`:`), over-long paths, symlinks or junctions that escape the root, and case-colliding names on case-insensitive filesystems.
- Generated file names come from the plan's sanitized, de-duplicated names (GENERATION.md section 4); they are never copied from raw OCR text.
- Writes are atomic (temp file plus `os.replace`) and never overwrite outside the output directory; overwriting requires explicit confirmation.

## 4. Inputs: decoding and limits
- Accepted: PNG, JPEG, WebP, single frame. Rejected: animated images, other formats, SVG input. Content is verified by decoding, not by extension.
- Limits (initial defaults): file size 50 MB, maximum side 16384 px, maximum 100 megapixels, checked from the header before full decode. Decompression-bomb checks are mandatory.
- Decoding and analysis run in worker subprocesses with time and memory limits. On Windows the intended mechanism is Job Objects for memory/CPU limits; this is verified in Phase 1 before being documented as enforced. If a limit cannot be enforced on a platform, the limitation is documented rather than assumed.
- Metadata is stripped; the normalized lossless artifact is what later stages read.
- SVG: the core only produces SVG itself (vector traces). SVG supplied by a plugin passes an allowlist sanitizer (no script, `foreignObject`, external references, `@import`, event attributes, data URLs with active content) before storage (IR_SPEC T-2).

## 5. Executing generated code

### 5.1 Tier 0: static rendering (the only automatic tier)
Static HTML/CSS output only: JavaScript disabled, fresh temporary browser profile, all network requests aborted, file access limited to the project directory, extensions and downloads disabled, browser sandbox left on, separate process with time and memory limits. Rendering a generated page is therefore not "running untrusted code" in the sense of build tools or scripts, but the page is still treated as hostile data (hence the restrictions).

### 5.2 Tier 1: build or run React/Next.js
- Never automatic. Each execution requires an explicit user action: a confirmation dialog in the desktop app listing exactly what will run, or an explicit CLI flag (`--allow-execute`) for that invocation.
- Requires an isolated execution boundary that passes the acceptance tests in 5.3. Until then Tier 1 is unavailable on user machines: React and Next.js output is generate-only, and the desktop preview is the static HTML rendering.
- Dependencies come only from the allowlisted template with a lockfile and integrity hashes; installs run with install scripts disabled; no dependency is ever derived from model output or the IR.
- CI exception: Screen2Code's own golden fixtures may be built in CI inside the ephemeral runner, which is the isolation boundary there. This never applies to user-provided projects.

### 5.3 Windows isolation: open spike (not solved)
Candidates to evaluate: a container with a WSL2 backend; Windows Sandbox (availability depends on the Windows edition and must be verified); a lightweight virtual machine; process-level restrictions alone (restricted token plus Job Object), which are expected to be insufficient for package managers and are listed only as a baseline to test against.

Acceptance tests (all must pass for a candidate to be adopted):
1. No access to the host filesystem except the mounted project directory (read-only source, writable output).
2. No network access after the pinned dependency install from an offline cache or lockfile.
3. No inherited environment variables, credentials, or tokens.
4. CPU, memory, and wall-clock limits enforced; forced termination on timeout.
5. No ability to start processes outside the boundary or persist after teardown.
6. Works from the desktop app and CLI with the user's installed prerequisites, with a clear message when prerequisites are missing.
Outcome of the spike is recorded in an ADR. Until that ADR is accepted, the statement "Tier 1 is unavailable" stays in the UI and docs.

## 6. Model output and prompt injection
- Provider outputs are untrusted data: parsed against schemas, size-limited, never executed, never interpolated into code, paths, or prompts without escaping.
- Providers get no tools, no filesystem access, and no network beyond their own endpoint (local by default). Prompts state that text in images is data. A model's refusal or injected instruction cannot change the pipeline because structure is inferred from evidence, not copied from model text (IR_SPEC section 2).
- Remote providers only on explicit opt-in; request contents follow the redaction profile.

## 7. Secrets, privacy, IPC
- Provider API keys are stored in the OS credential store (Windows Credential Manager) and never written to project files, the IR, the generation plan, logs, reports, or run records. Logs scrub known key patterns.
- No telemetry. Logs exclude image content and OCR text by default; a debug store that includes them is opt-in and local.
- Redaction (IR_SPEC section 16) is the privacy control for personal data in screenshots; it does not by itself make a project safe to share, and the docs say so.
- Desktop IPC: JSON-RPC over stdio between the Tauri shell and the sidecar; no network listener. The webview loads only bundled content under a strict content security policy; the Tauri command allowlist is minimal. Generated HTML previews appear in a sandboxed frame without script permission, served from a custom protocol restricted to the project directory.
- The UI never injects raw HTML from the IR or from generated output.

## 8. Supply chain and releases
- Python dependencies locked with hashes; JavaScript lockfile with integrity hashes; CI fails on unpinned dependencies.
- License audit and an SBOM (CycloneDX) per release; `THIRD_PARTY_LICENSES` generated (ADR D4).
- Models: checksum-verified from a signed registry manifest (MODEL_STRATEGY.md section 4). The Chromium revision for rendering is pinned and checksum-verified.
- Windows binaries are code-signed; the sidecar build and signing sit behind the packaging abstraction (ARCHITECTURE.md section 10). Antivirus false positives are tracked per release and reported to vendors.
- Plugins are arbitrary Python code and are therefore trusted-code: disabled by default, enabled per plugin by the user, loaded only from the user's environment, and documented as outside the sandboxing model. A plugin cannot change the trust boundary rules; the validator and the confined writer sit below plugins.

## 9. Security tests (required before the matching feature is "done")
| Area | Tests |
|---|---|
| Paths | traversal strings, reserved names, long paths, symlinks/junctions, case collisions, alternate streams |
| Images | decompression bomb, truncated and polyglot files, oversized dimensions, animated files |
| Injection | hostile strings (`<script>`, `"><img onerror=...>`, `</style>`, template markers, RTL overrides) in OCR text, names, alternatives pass through IR to every generator and render inertly (golden tests) |
| IR | `extensions` data and asset references cannot cause file access or execution |
| Render | Tier 0 settings verified: a fixture page attempting a network request, script, or file read outside the project fails |
| Plans | stale or tampered plan is rejected by hash |
| Secrets | keys never appear in logs, run records, reports (scan tests) |
| IPC | malformed JSON-RPC, oversized messages, unknown methods |
Fuzzing of the image import path and the IR parser is added once those exist.

## 10. Reporting
Vulnerabilities are reported through the process in the repository-root `SECURITY.md` (private advisory channel, response targets, supported versions). That file is part of Phase 1 scaffolding; until it exists the repository is not public.

## Redaction scope (implemented)

`privacy.redact_text: true` removes recognized text values from the IR, evidence, names, generated code and reports; every redaction is an auditable record and counted as an evaluation exclusion.
It does **not** mask pixels: the imported screenshot and extracted raster assets remain in the project directory. Do not share a project directory on the strength of this mode alone.
